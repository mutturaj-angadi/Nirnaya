# Solver algorithm

The CPU engine applies a lower-bound shift (free variables split into positive/negative parts), appends finite-upper-bound rows, and uses sparse equality/inequality matrices with slack, surplus, and artificial columns. Phase I minimizes the sum of artificial variables. A positive Phase I optimum beyond `feasibility_tol` reports infeasibility. At a feasible Phase-I optimum, zero-valued artificial basic variables are pivoted out with deterministic degenerate pivots. A row with no eligible non-artificial pivot is redundant in the feasible system and is removed. This transition is important: otherwise a zero Phase-II artificial cost could let an artificial variable become positive and conceal a violated original equation. Phase II then optimizes the requested signed objective over the original/slack columns.

Each revised-simplex iteration solves for primal basic values and dual multipliers, computes sparse reduced costs, selects the smallest-index improving nonbasic variable, solves the entering direction, and applies a vectorized minimum-ratio test. The smallest basic-variable index breaks ratio ties. This is Bland's deterministic anti-cycling rule. Singular or non-finite basis solves return `NUMERICAL_ERROR`; an improving column with no eligible leaving row proves unboundedness.

The implementation keeps the full constraint matrix and basis sparse and uses SciPy sparse LU as a base factorization. A bounded product-form eta chain represents subsequent basis pivots: FTRAN applies updates in insertion order and BTRAN applies transposed updates in reverse order. The solver refactorizes after 31 stored updates, on a scale-small pivot, or when periodic primal/dual basis residual checks exceed the existing tolerances. The cached sparse transpose supports pricing; basis masks are maintained across pivots; ratio candidates are vectorized. This preserves the deterministic pivot rule while avoiding an LU refactorization at every pivot. Dual simplex, validated sensitivity/certificate output, and broader numerical scaling remain future work. Current target workloads are continuous LPs whose basis fits available memory and where deterministic correctness/debuggability is preferred over advanced warm-start or crossover features; this does not imply competitiveness on arbitrary industrial LPs.

There is no public `SolverEngine` strategy registry yet because only one algorithm is implemented. Future algorithms should be added behind the solver API only when implemented, independently tested, and reference-validated.
